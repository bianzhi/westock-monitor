## 一、项目概览

### 1.1 项目定位 ★★★★☆

面向 A 股投资者的**申万二级板块资金流监控系统**，核心链路：

```
全市场 134 板块概览  →  按强度/净额率筛选强/弱板块  →  下钻单板块分钟级 + 历史 n 日
        │                       │                              │
   /api/sectors          /api/strength/ranking        /api/sectors/{code}/minute
```

**亮点：**
- 需求清晰，符合投研"概览 → 筛选 → 下钻"的实际工作流
- 全栈自包含：`./start.sh` 一键启动后端 + 前端 + 采集循环
- 数据零外部服务依赖：全部数据通过 `westock-data` CLI（npx 执行）+ 可选 Tushare Token 获取
- 已实现**一级行业聚合视图**（`/api/sectors/l1-summary` + 前端 Tab），这是 v1 评审列出的"缺失功能 F1"，现已落地

## 二、数据准确度

### 2.1 数据链路总览 ★★★★☆

```
westock-data CLI (fund flow)
  ├─ MainNetFlow          主力净流入(元) = MainInFlow - MainOutFlow
  ├─ MainInFlow/OutFlow   主力流入/流出(元)
  ├─ RetailInFlow/OutFlow 散户流入/流出(元)
  ├─ MainNetFlow5D/10D/20D 近N日累计主力净流入(元)
  └─ ClosePrice / EndDate
        ↓
  westock_fund_metrics.py
  ├─ 成交额 = calc_turnover(method=all)  →  MainInFlow + MainOutFlow + RetailInFlow + RetailOutFlow
  ├─ 净额率 = MainNetFlow / turnover × 100
  └─ 近N日累计净值字段透传
        ↓
  collector.py:collect_daily_records
  ├─ 今日：实时 fund flow
  └─ 历史 T-1..T-(n-1)：分段阶梯差分估算 + 交易日历取真实日期
        ↓
  strength.py:calc_aggregate_net_rate
  └─ 近n日聚合净额率 = Σ净流入 / Σ成交额 × 100
        ↓
  config.SCALE_THRESHOLDS → 5 档判定
```

**链路评价：**
- 所有数据来源有明确链路，不是魔法数字
- 对已废弃接口（`asfund`/`minute`/`quote`/`board` 在 1.0.5 已废弃）有明确回避，代码注释标注了实测结论
- 申万板块清单有 `sw2021_sectors.py` 作为权威来源，不是凭记忆编造（这是项目记忆里反复强调的要点）

### 2.2 历史数据估算 ★★★☆☆ —— 仍存边界风险

**当前做法（`collect_daily_records`，已比 v1 改进）：**
```python
# 分段阶梯差分
seg_1_4   = (MainNetFlow5D  - today_net)   / 4      # T-1~T-4
seg_5_9   = (MainNetFlow10D - MainNetFlow5D)  / 5   # T-5~T-9
seg_10_19 = (MainNetFlow20D - MainNetFlow10D) / 10  # T-10~T-19
# 日期用 get_last_n_trading_days(n+1, today) 取真实交易日
```

**仍存在的 3 个边界风险（v1 完全没识别）：**

| # | 风险 | 详情 | 严重度 |
|---|------|------|--------|
| H1 | **分段分母硬编码 4/5/10，前提是 westock 5D/10D/20D 严格等于 5/10/20 个交易日** | 若 westock 的"5D"口径是"含今日共 5 个交易日"，则 `seg_1_4 = (5D - today)/4` 正确；但若口径是"自然日"或"含今日 + 4 个历史交易日共 5 个"则分母错。代码注释未验证 westock 字段口径 | 中 |
| H2 | **非交易日查询时日期切片错位** | `get_last_n_trading_days(n+1, today)` 在 today 非交易日时，会从 today 往回找第一个交易日当 `trading_days[0]`，但 `history_days = trading_days[1:n+1]` 仍按"T-1"语义填值——实际上 `trading_days[0]` 已经是上一个交易日，切片后会把上一个交易日错当成 T-1 两次（一次作今日、一次作 T-1） | 中 |
| H3 | **超出 20D 范围（n>20）回退兜底** | `avg = seg_10_19 or seg_5_9 or seg_1_4 or 0`——n=20 时 T-11~T-19 全填 `seg_10_19` 同一均值，图表后段呈水平线。但前端 `Select` 最大只到 `n=20`，刚好踩边界 | 低 |

**建议：**
1. 在 `westock_fund_metrics.py` 加一个 `verify_main_net_flow_window()` 自检函数，用真实板块数据验证 5D/10D/20D 口径
2. `collect_daily_records` 第 359 行改为 `get_last_n_trading_days(n, today)` 并单独处理今日，避免切片歧义
3. n>20 时前端禁用或后端返回警告

### 2.3 成交额计算 ★★★☆☆

**当前方案：** `config.TURNOVER_METHOD = "all"`，即
```
成交额 = MainInFlow + MainOutFlow + RetailInFlow + RetailOutFlow
```

**仍存问题：**

| # | 问题 | 详情 |
|---|------|------|
| T1 | **"all" 口径仍 ≠ 全市场成交额** | 主力 + 散户只覆盖了大单/超大单/小单，缺中单部分。实测"all"约为全市场成交额的 70-85%。比"main"口径（10-30%）更接近真实，但仍有系统性偏低 |
| T2 | **历史成交额完全缺失** | `collect_daily_records` 历史记录 `turnover=None`，`_build_summary` 用"今日成交额 → 流通市值×规模换手率"兜底。今日成交额开盘前为 0 也无效，最终全走流通市值×换手率路径 |
| T3 | **兜底换手率按规模分档（大盘 1% / 中盘 2% / 小盘 3%）** | 这是 v1 之后改进的，比一刀切 2% 合理。但同规模内部差异仍大（银行 0.3% vs 证券 5%），历史净额率估算仍有 ±30% 波动 |

**建议：**
- README 加"数据精度说明"章节，明确告知净额率是基于 westock 字段估算，并非交易所官方数据
- 长期看，考虑引入 eastmoney 的板块成交额接口做交叉校验

### 2.4 流通市值精度 ★★★☆☆

**双路兜底方案：**
- 方案 A（Tushare `daily_basic`）：个股 `circ_mv` 字段累加，**相对最准**，但需有效 Tushare Token
- 方案 B（westock 反推）：`MainInflowCircRate = |MainNetFlow| / circ_mv × 100` 反推，精度取决于字段小数位（实测最小 0.01%）

**问题：**

| 问题 | 影响 | 建议 |
|------|------|------|
| 无 Tushare 时依赖反推，精度 ±20% | 大/中/小盘分档可能错位（边缘板块如 0.98 万亿被分到小盘），导致用错阈值做强度判定 | 在 `sector_circ_mv` 表记录 `is_estimated`，前端对"反推"来源的流通市值加 Tooltip 提示 |
| 长假后回溯窗口不足 | `_find_valid_trade_date` 只往前回溯 7 天，国庆 7 天 + 周末 = 9 天无数据，会拿 0 条记录直接回退方案 B | lookback 至少延长到 15 天 |
| 成分股采集失败无重试 | `collect_constituents_all_sectors` 失败则板块无成分股列表，流通市值也为空 | 加指数退避重试 |

### 2.5 分钟级差分 ★★★☆☆

**做法：** 每分钟调一次 fund flow，拿 `MainNetFlow` 当日累计值，与上一分钟快照差分得到 `minute_delta`。

**问题：**

| # | 问题 | 详情 |
|---|------|------|
| D1 | **不是真"分钟级"** | 接口只返回累计值，差分值是两次调用的增量。接口本身有缓存/延迟，两次调用之间的成交量可能不完全是这 60 秒内的 |
| D2 | **开盘第一分钟无差分** | 9:30 第一条快照的 `minute_delta = main_net_flow - 0`，等于当日累计，前端图表上第一根柱子会异常高 |
| D3 | **成交额差分缺失** | 只对 `main_net_flow` 做了差分，`turnover` 是每分钟的当日累计值，没有差分出本分钟成交额 |

**建议：**
- 对 `turnover` 同样做差分，让分钟图同时展示"本分钟净流入"和"本分钟成交额"
- 过滤开盘第一条的异常差分值（或标记 `is_open_anchor: true`）

### 2.6 边界情况 ★★★☆☆

| 场景 | 当前行为 | 问题 |
|------|---------|------|
| **westock CLI 全挂** | `fund_flow` 返回空列表 → `flow_map = {}`，所有板块今日数据全为 None | 前端显示全为"-"，用户不知道是接口挂了还是真没数据。建议在 `errors` 中区分"无数据"和"接口异常" |
| **部分板块无数据** | 134 个中只有 80 个返回 → 其余 54 个被静默跳过 | `errors` 里只有 `westock_low_coverage` 标记，前端不展示。建议加 `coverage_rate` 字段 |
| **n=20 时数据极稀疏** | n=20 但接口只到 20D 累计，历史 19 天全部平均估算 | 用户选 n=20 时看到 19 条估算柱状图，体验差。建议 n>5 时图表上加警告标注 |
| **流通市值为空时强度判定** | `calc_strength` 中 `circ_mv_yi is None` → `get_scale` 兜底为"小盘"，仍走 5 档判定 | 合理兜底，但前端不区分"真小盘"和"无数据所以小盘"，建议加 `strength_confident: false` |

## 三、代码质量

### 3.1 模块结构 ★★★★☆

```
config.py              全局配置，环境变量覆盖
sectors.py             申万二级板块代码（134 个硬编码 + 接口刷新）
sw2021_sectors.py      申万 2021 版权威清单（31 一级 / 134 二级）
westock.py             westock-data CLI 封装（subprocess + 批量分批）
westock_fund_metrics.py  fund flow 字段 → 成交额/净额率指标
trading_calendar.py    A 股交易日历（Tushare → 缓存 → weekday 启发式）
collector.py           采集层（分钟级差分 + 日级实时拉取 + 板块列表刷新）
circ_mv_collector.py   流通市值采集（方案 A Tushare / 方案 B westock 反推）
strength.py            强度计算（5 档判定 + 分段线性插值 + n 日窗口）

data_cache.py          内存缓存层（启动预热 + 后台 60s 刷新）
app.py                 FastAPI 后端
```

**评价：**
- 模块划分清晰，职责单一（采集 / 计算 / 存储 / API / 缓存分层）
- 每个模块都有 `__main__` 自检，方便单模块验证
- 类型注解使用规范（`Optional[Dict[str, Any]]` 等）
- 中文 docstring 与代码逻辑一致，无误导性注释

### 3.2 仍存的代码问题 ★★★☆☆

| # | 问题 | 位置 | 严重度 |
|---|------|------|--------|
| C1 | **`calc_aggregate_net_rate` 与 `_build_summary` 逻辑高度重复** | `strength.py:169-183` vs `app.py:734-748` | 低 | 两段代码做的事几乎一样（成交额缺失兜底 + 累加），应抽公共函数 |
| C2 | **`_build_summary` 的成交额兜底链有歧义** | `app.py:738-744` | 中 | 注释说"今日成交额 → 流通市值×2% 兜底"，但实际代码先尝试 `today_turnover`，若今日开盘前为 0 则走 `fallback_turnover`。问题在于：**今日成交额会作为所有历史日期的成交额近似**，若今日开盘不久成交额才 100 亿，历史 4 天都被填成 100 亿，历史净额率被系统性低估。建议历史日直接用 `fallback_turnover`，跳过 `today_turnover` 兜底 |
| C3 | **`get_sectors` 在 `force_refresh=True` 时同步阻塞调用 `refresh_cache()`** | `app.py:287-289` | 中 | `refresh_cache` 内部调 `_load_all_data` 耗时 2-5s，期间 uvicorn 单 worker 阻塞所有其他请求。建议 `force_refresh` 改为后台触发 + 轮询状态，或加请求去重锁 |
| C4 | **`startup_event` 用 `@app.on_event("startup")` 装饰器** | `app.py:784` | 低 | FastAPI 0.93+ 已废弃 `on_event`，推荐用 `lifespan` 上下文管理器。当前 `fastapi>=0.110.0` 仍兼容，但未来版本会移除 |
| C5 | **CORS 配置 `allow_origins=CORS_ORIGINS + ["*"]`** | `app.py:86` | 中 | 加 `["*"]` 等于完全放开 CORS，且 `allow_credentials=True` 与 `*` 同时存在会被浏览器拒绝。生产环境应移除 `["*"]` |
| C6 | **`storage.py` 全局单例 + RLock，但 `_get_conn` 每次新建连接** | `storage.py:62-74` | 低 | SQLite 连接开销小，但高频请求下仍有损耗。建议用连接池或线程局部连接 |
| C7 | **`data_cache._load_all_data` 中 `circ_mv_raw` 的来源未注释清楚** | `data_cache.py:120` | 低 | `collect_all_sectors_daily` 返回 `(daily_map, circ_mv_raw)`，但 `circ_mv_raw` 实际是什么——是 fund flow 反推的流通市值？还是 sector_circ_mv 表？需要追到 `collector.py:collect_all_sectors_daily` 才能确认。建议加类型注解 + 注释 |
| C8 | **前端 `App.jsx` 单文件 576 行，含 L2 表 + L1 表 + 行展开 + 图表组装** | `frontend/src/App.jsx` | 低 | 建议拆分为 `L2Tab.jsx` / `L1Tab.jsx` / `SectorDetail.jsx`，单文件超过 300 行维护成本上升 |

### 3.3 测试覆盖 ★★☆☆☆

**现状：** 零自动化测试。每个模块只有 `__main__` 手动自检，依赖真实 westock CLI 和网络。

**风险：**
- `calc_aggregate_net_rate` 的成交额兜底链（今日成交额 → 流通市值×换手率）逻辑复杂，无单测覆盖
- `collect_daily_records` 的分段差分 + 交易日历切片边界（H1/H2）无单测验证
- 任何字段口径变化（westock 升级）都无人察觉

**建议：**
- 优先为 `strength.py:calc_aggregate_net_rate` 和 `collector.py:collect_daily_records` 加单测（pytest + mock fund flow 返回）
- 用 GitHub Actions 跑 `python -m pytest tests/` + `npm run build` 做 CI

### 4.2 色彩与视觉编码 ★★★★☆

**强度标签配色：**
```
强    #e74c3c (红)   —— 暖色，符合"强=好"的直觉
偏强  #f39c12 (橙)   —— 过渡色
普通  #95a5a6 (灰)   —— 中性
偏弱  #3498db (蓝)   —— 冷色
弱    #2c3e50 (深蓝) —— 冷色
```

**问题：**
- "弱"用深蓝 `#2c3e50`，在小字号下几乎呈黑色，与"偏弱"的亮蓝 `#3498db` 区分度不够。建议"弱"用深绿 `#27ae60` 或保持蓝色但加粗/加边框
- "强"的红 `#e74c3c` 与 A 股红色=涨 一致，但"弱"的深蓝在一些行情软件中代表"平盘/中性"，语义有歧义

**净流入着色：**
```
正 → 红色 #e74c3c (中国习惯：红涨)
负 → 绿色 #2ecc71 (中国习惯：绿跌)
```
正确，符合国内用户习惯。

### 4.3 图表可读性 ★★★☆☆

**`DailyHistoryChart`（近 n 日柱状图）：**

## 五、工程可靠性

### 5.1 启动与预热 ★★★★☆

**流程：**
1. `startup_event` 后台线程预热 westock CLI（`fund_flow(["pt01801081"])`）
2. `init_cache(n=10)` 同步加载全板块 10 交易日数据（2-5s）
3. `start_background_refresh(interval_sec=60)` 启动后台 60s 定时刷新

**优点：**
- 启动不阻塞，FastAPI 立即可服务
- 后台 60s 定时刷新只在交易时段执行，非交易时段不浪费 API 调用
- 内存缓存命中后 API 响应 <5ms（v1 评审里"刷新阻塞主线程"的 P2 问题已被缓存层解决）

**问题：**

| # | 问题 | 详情 |
|---|------|------|
| R1 | **缓存未就绪时 API 直接 503** | `get_sectors` 中 `if not is_ready(): init_cache(n=10)`，若 init_cache 失败则返回 503。但前端 `loadSectors` 的 catch 只显示"加载失败"，未提示"正在预热，请稍候"。建议前端区分 503 错误码，显示"数据预热中..." |
| R2 | **后台刷新线程无异常熔断** | `_background_refresh` 中 `except Exception: logger.warning`，但若 westock CLI 持续挂掉，每 60s 仍会重试，刷错误日志。建议加连续失败计数器，N 次失败后拉长间隔 |
| R3 | **`init_cache` 失败后 `_ready` 仍为 False，但无重试机制** | 启动时若网络抖动导致 `_load_all_data` 抛异常，缓存永远不会就绪，直到下次 `force_refresh=True` 的请求触发。建议启动时 init_cache 失败则 30s 后自动重试 |

### 5.2 并发与线程安全 ★★★☆☆

**并发模型：**
- FastAPI uvicorn 单 worker（`start.sh` 未指定 `--workers`）
- 后台采集循环、后台缓存刷新都是 daemon 线程
- `data_cache` 用 `threading.RLock` 保护全局 `_cache` dict
- `storage.py` 用 `sqlite3` + `check_same_thread=False` + RLock

**问题：**

| # | 问题 | 详情 |
|---|------|------|
| P1 | **`force_refresh=True` 同步阻塞 uvicorn** | 如前述 C3，`refresh_cache()` 同步调 `_load_all_data`（2-5s），期间 uvicorn 单 worker 阻塞所有其他请求 |
| P2 | **多个并发 `force_refresh` 请求会重复拉取** | 无请求去重锁，若前端用户连续点 5 次刷新按钮，会触发 5 次 `refresh_cache`，每次都全量拉 134 板块 |
| P3 | **`data_cache._lock` 是 RLock，但 `_load_all_data` 内部又调 `collect_all_sectors_daily`，若该函数也尝试获取同一锁会死锁** | 实测 `collect_all_sectors_daily` 不访问 `_cache`，不会死锁，但这个隐含约束没有代码注释说明，未来重构容易踩坑 |

### 5.3 错误处理与日志 ★★★☆☆

**优点：**
- 每个模块都有 `logger = logging.getLogger(__name__)`
- 关键路径有 `logger.info` / `logger.warning` / `logger.error` 分级日志
- 日志写入 `logs/` 目录（实测有日志文件）

**问题：**

| # | 问题 | 详情 |
|---|------|------|
| E1 | **westock CLI 调用失败时错误处理不一致** | `westock.py` 中 CLI 超时/返回非零退出码的处理逻辑分散，部分函数返回 `None`，部分返回 `[]`，部分 raise。建议统一为"返回空列表 + logger.warning" |
| E2 | **API 层 HTTPException 状态码使用不规范** | `get_sectors` 在缓存未就绪时返回 503，在 `no cached sector data` 时返回 500。但 500 应该是"服务器内部错误"，"无缓存数据"更像是 503（服务暂不可用） |
| E3 | **日志未配置 RotatingFileHandler** | 长期运行下 `logs/` 目录会无限增长。建议用 `logging.handlers.RotatingFileHandler` 限制单文件大小 |

### 5.4 配置管理 ★★★★☆

**优点：**
- 所有配置集中在 `config.py`，支持环境变量覆盖
- 路径配置用 `pathlib.Path`，跨平台友好
- 规模分档阈值、换手率兜底、采集间隔等都可配

**问题：**

| # | 问题 | 详情 |
|---|------|------|
| CFG1 | **无 `.env.example` 文件** | 用户不知道可以配置哪些环境变量。建议在项目根目录加 `.env.example` 列出所有可配项 |
| CFG2 | **`CORS_ORIGINS` 硬编码了两个 localhost 端口** | 生产部署时需要改源码，建议改为环境变量 `CORS_ORIGINS=http://localhost:3000,http://localhost:5173` |

## 八、总结

### 8.1 项目优点

1. **数据链路清晰可追溯**：每个指标都能追溯到 westock fund flow 的具体字段，不是魔法数字
2. **工程链路完整**：启动预热 → 内存缓存 → 后台定时刷新 → API 响应 <5ms，整条链路跑通
3. **配置灵活**：n 日窗口、采集间隔、规模阈值、成交额口径、换手率兜底等全部支持环境变量覆盖
4. **文档与代码同步性较好**：README 的 API 示例与实际响应字段一致，docstring 与代码逻辑一致
5. **一级行业聚合视图**作为 v1 之后的增量功能，已实现并接入前端 Tab

### 8.2 项目风险

1. **历史数据估算的边界风险未验证**：分段差分分母 4/5/10 的前提（westock 5D/10D/20D 口径）未做实测验证，非交易日查询时日期切片会错位
2. **零自动化测试**：所有模块依赖 `__main__` 手动自检，任何字段口径变化（westock 升级）都无人察觉
3. **流通市值精度依赖 Tushare Token**：无 Token 时回退方案 B（反推），精度 ±20%，可能影响大/中/小盘分档
4. **CORS 完全放开**：`allow_origins=CORS_ORIGINS + ["*"]` 在生产环境是安全风险
5. **`force_refresh` 阻塞 uvicorn**：用户点一次"刷新"按钮，2-5s 内所有其他请求被阻塞

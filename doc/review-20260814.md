# Westock Monitor 产品设计评审报告（独立第四轮 · 2026-08-14）

> 评审基线：working tree（HEAD `6fc87ca`，含"采集/展示分离"refactor `65da808` 与"线程守护器" `6fc87ca` 等 8 个新 commit）。
> 评审方法：忽略前三轮结论，从现场代码独立判断。核心框架：**用户故事驱动 vs 接口能力驱动**。

## 一、缺陷清单

### P0 · 强度档位存在三套并存、互相矛盾的口径

**P0-1 · 告警判定口径固定 n=5，与展示口径解耦**
- **定位**：`data_cache.py:338` `check_strength_alerts` 调用 `calc_sector_strength(records, circ_mv_yi, STRENGTH_WINDOW_N)`，其中 `STRENGTH_WINDOW_N=5`（`config.py:50`）；而前端 Header 的 n 可切 3/5/10/20（`App.jsx:538`），宽表强度按用户所选 n 计算。
- **危害**：用户在宽表切到 n=10 看到某板块"偏强"，告警 Tab 却写"普通→偏强"（按 n=5 算）——同一板块、同一时刻，两个入口给出互相矛盾的档位结论。
- **为何是产品设计问题**：告警是给用户的产品功能，不是开发者诊断。它的判定口径必须与用户当前观测口径一致，否则告警本身成为噪声源。这是"接口能力驱动"的典型——后端把告警检测做完了，却没接上用户的主观测旋钮。

**P0-2 · 概念板块"宽表"与"详情"是两个口径**
- **定位**：概念板块宽表 `get_concept_sectors` 用近 n 日真缓存（`concept_daily`）算强度；而详情页 `get_sector_detail` 的 concept 分支（`app.py:864`）`records = [{"date": today_str, "net_flow": today_net, "turnover": today_turnover}]`——**只取今日一条**，n 参数形同虚设。
- **危害**：用户扫概念宽表看到某板块"强"，点开行详情看到强度标签却是"普通"——因为宽表按近 5 日聚合、详情按今日单日，两个数源完全不同。
- **为何是产品设计问题**：宽表和详情是同一对象（同一板块）的两个视图，产品上必须同源。详情页为了"快速返回"只取今日一条，等于牺牲了强度结论的一致性去换一个没有产品价值的性能指标。

**P0-3 · 概念板块复用二级板块的列结构，导致主列全空、自选列错乱**
- **定位**：`App.jsx:386` 的 `columns` useMemo 定义了一次（含 ★自选、流通值、规模、今日成交额…），二级板块 Tab 与概念板块 Tab 共用同一个 `columns`（`App.jsx:777` 与 `App.jsx:930`）。但概念板块 `circ_mv_yi=None`、`scale="小盘"`（`get_sector_detail:874-875`），流通值与规模列在概念 Tab 全是 "-" 或恒"小盘"；★自选列把二级板块代码空间（pt01）与概念板块代码空间（pt02）混进同一个 watchlist。
- **危害**：概念板块宽表一屏里，"流通值(亿)"列全部 "-"、"规模"列全部"小盘"、★列点了一个概念板块却和二级板块自选混在一起置顶。用户无法从概念宽表获取任何流通市值信息，且自选列表被两个语义空间污染。
- **为何是产品设计问题**：概念板块在产品定位上是"辅助观测"（无量级指标、变动快、代码空间独立），却强行套用了二级板块主看板的完整列结构。这是典型的"复用已有组件省事，而不是按产品语义设计"。

**P0-4 · 默认首屏 Tab 是概念板块，而非产品主叙事**
- **定位**：`App.jsx:41` `useState("concept")`——应用启动默认切到概念板块 Tab。
- **危害**：产品标题是"申万二级板块资金流监控"（README 标题），二级板块宽表才是主看板。首屏却默认概念板块——新用户打开看到的是一个无量级、无流通市值、强度口径分裂的辅助视图，误以为这就是产品全部。
- **为何是产品设计问题**：首屏 Tab 是产品叙事的入口。工程选"concept"疑似因为概念路由不依赖 data_cache 预热、首屏加载快——即"哪个 Tab 数据就绪快就默认哪个"，而非"哪个 Tab 是产品主叙事就默认哪个"。

### P1 · 产品叙事断裂

**P1-1 · "暂无数据"不区分状态，用户无法判断是坏还是没到点**
- **定位**：refactor `65da808` 后，`get_sector_minute`（`app.py:925` 注释）、`get_minute_compare`（`app.py:1052` 注释）在数据库无数据时直接返回空，前端 `CompareChart.jsx:25` 统一渲染"暂无数据"。
- **危害**：用户看到"暂无数据"，分不清四种情况——① 还没到采集时间；② 后台采集线程挂了（守护器在重启中）；③ 盘前无数据；④ 该板块真无数据。这四种的产品应对完全不同，但产品只给了一种无差别提示。
- **为何是产品设计问题**："采集/展示分离"是架构正确方向，但分离后"数据为空"的语义变成了产品必须回答的问题——产品没回答。用户面对空图时没有任何诊断线索，只能猜。

**P1-2 · Header 三个"刷新"语义不同，主次不分**
- **定位**：`App.jsx:583`"刷新"（刷宽表数据）、`App.jsx:599`"刷新板块列表"（刷申万清单）、`App.jsx:622`"刷新概念"（补全概念白名单），三个按钮并排，语义完全不同但都叫"刷新"。另有"采集"按钮（`App.jsx:586`，开发者诊断）与主操作并排。
- **危害**：普通用户首屏面对 7 个交互元素，无法分辨"刷新"和"刷新板块列表"的区别；"采集"对用户无意义却占据黄金位置。
- **为何是产品设计问题**：Header 是全局操作区，应主次分明——主操作（刷新宽表）突出，诊断/管理操作（采集/刷清单/刷概念）收进二级菜单或设置抽屉。现在全平铺，是"接口能力都做了就都摆出来"。

**P1-3 · 认证是"可选"的，且降级无声，用户误以为有云端同步**
- **定位**：`AuthGuard.jsx:16-20` 当 Supabase 未配置时 `setAuthed(true)` 直接放行；`supabase_user.py` 所有读写未配置时静默降级返回空/默认值；前端 `App.jsx:56-101` 的 watchlist/告警阈值降级到 localStorage。但 UI 上无任何"当前是本地模式、数据不跨设备、不云同步"的标识。
- **危害**：用户登录后（或未登录直接进入）配置了自选板块和告警阈值，以为"已保存"（`AlertsTab.jsx:100` 甚至提示"已保存到本地"），但换个设备/清浏览器缓存数据就全没了。用户对"我的数据到底存哪、会不会丢"没有正确预期。
- **为何是产品设计问题**：千人千面功能的产品价值是"我的数据跟着我走"，但降级路径让这个价值在默认部署（未配 Supabase）下是**假的**。产品没有用明确的标识告诉用户"你现在是本地模式"，而是让用户自己从"已保存到本地"这句含糊提示里去猜。

**P1-4 · 分钟缓存保留期：文档承诺 5 日，实现 2 日**
- **定位**：`config.py:111` `MINUTE_CACHE_DAYS=2`（注释写"2026-08-11 用户要求 2 日"）；`README.md:33` 架构图写"仅缓存最近五日"、`README.md:186` 配置表写"默认 5"。
- **危害**：用户按 README 预期盘后能看近 5 日分时，实际第 3 天起数据已被 `cleanup_old_minute_data` 清掉。盘后复盘的核心场景（看前几天分时走势）被配置和文档的分裂悄悄削弱。
- **为何是产品设计问题**：产品决策在 2 日和 5 日之间反复（`647deed` 改 2、`391c189` 改 5、后续又改回 2），但 README 没跟着同步。用户视角的承诺（5 日）与实现（2 日）分裂，且这个分裂对"盘后复盘"这一核心场景是实质伤害。

### P2 · 次要

**P2-1 · README 与前端 Footer 数据源描述与实现矛盾**
- **定位**：`collector.py:268` 注释明确"腾讯原 HTTP 接口已死，净额率改用 westock 自身字段计算"；但 `README.md:3`、`README.md:24` 架构图、`App.jsx:954` Footer 仍写"腾讯原始 HTTP 接口""腾讯自选股"。
- **危害**：数据源是监控产品的信任根基。用户按 README 理解数据从腾讯 HTTP 来，实际是 westock CLI + Tushare（数据源体检徽标显示的三源是 westock/tushare/trading_calendar），对不上。
- **为何是产品设计问题**：产品叙事与实现长期分裂没人维护，README 描述的是已经下线的架构。

**P2-2 · "近5日净额率 Top15" 图表标题与内容不一致**
- **定位**：`Charts.jsx:174-208` `NetRateCompareChart` 标题写"近5日净额率 Top15"，但图内同时画"近3日净额率"和"近5日净额率"两条柱，排序按近5日。
- **危害**：用户看到标题"近5日 Top15"，图里却出现两套数据，且排序只依据其中一套（近5日）——近3日的柱子可能不单调、显得"乱序"，用户误以为图表错了。
- **为何是产品设计问题**：图表标题是用户理解图的第一锚点。标题只提近5日，图里却混入近3日，叙事与呈现不一致。

## 三、一句话总结

**这个工程在架构层已从"接口能力驱动"走向正确方向——采集/展示分离、线程守护、测试覆盖都到位了，但产品叙事侧的系统性病灶仍在：强度档位存在三套并存且互相矛盾的口径（告警 n=5、宽表 n 可切、概念详情只用今日），导致用户在宽表/详情/告警三个入口看到同一板块的三种不同档位结论；同时"概念板块"这个无量级、无流通市值的辅助观测，被赋予了默认首屏位置和二级板块的完整列结构，反过来让"申万二级板块"这个产品主叙事失焦。**

P0 四条（P0-1~P0-4）本质是同一个问题的不同侧面：**工程把"有数据/有接口"当成了"产品做完了"，而没有问"用户在这一屏上到底该看到什么、该相信哪个数字"。**

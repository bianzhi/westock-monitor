## 一、产品角度

### 1.1 产品定位与用户价值 ★★★★☆

**优点：**

- **需求明确**：面向 A 股投资者，提供申万二级板块维度的主力资金流监控 + 强度判定。从"全市场 134 板块 → 筛选强/弱板块 → 下钻单板块详情"的漏斗链路清晰，符合投研实际工作流。
- **门槛低**：`./start.sh` 一键启动，自动检查环境、安装依赖，对非技术用户友好。
- **无外部依赖服务**：全部数据通过 westock-data CLI（npx 执行）和可选 Tushare Token 获取，不需要自建数据库或购买数据服务，降低了运维成本。
- **配置灵活**：n 日窗口、采集间隔、规模阈值、端口等全部支持环境变量覆盖，适配不同策略需求。

**问题与建议：**

| # | 问题 | 严重度 | 建议 |
|---|------|--------|------|
| P1 | **缺交易日历校验**：`collect_daily_records` 用 `timedelta(days=i)` 直接倒推日历日，周末/节假日被当成交易日，导致历史日期的 `date` 字段含非交易日，且估算值被错误分配 | 高 | 引入交易日历（Tushare `trade_cal` 或本地维护一份 A 股交易日列表），`DISPLAY_DAYS` 应跳过非交易日 |
| P2 | **刷新按钮会阻塞主线程**：`/api/sectors` 每次请求都实时调 westock fund flow（134 板块 × 分批并发），非交易时段约 2-5s，交易时段可能更久。前端无进度反馈，用户可能重复点击 | 中 | 加请求去重（`loading` 状态已有但不够），后端加短期缓存（如 30s），避免同一秒内重复拉取 |
| P3 | **强/弱板块 Top 排行只有 10 条**：`/api/strength/ranking` 的 `top=10` 硬编码在前端，用户无法自定义 | 低 | 加前端输入框或下拉，允许 10/20/50 |
| P4 | **缺"板块对比"功能**：用户经常需要对比 2-3 个相关板块的资金流趋势，当前只能逐个展开 | 中 | 加多选行 + 对比图表按钮，或加一个"自选板块"列表 |

## 二、数据准确度

### 2.1 数据源可靠性 ★★★★☆

**数据链路总览：**
```
westock-data CLI (fund flow)  →  主力净流入 MainNetFlow（当日累计 + 5/10/20 日累计）
                               →  主力流入/流出额
                               →  成交额（自算：MainInFlow + MainOutFlow）
                               →  净额率（自算：MainNetFlow / 成交额）

circ_mv_collector            →  流通市值（成分股反推累加，方案A Tushare / 方案B westock反推）

sw2021_sectors.py             →  板块代码/名称/行业归属（134个，申万2021官方标准）
```

**优点：**
- 所有数据来源有明确链路，不是魔法数字
- 对已废弃接口（asfund/minute/quote/board）有明确回避，代码注释标注了实测结论
- 流通市值有双路兜底（Tushare 直取 → westock 反推），失败率可追踪（`fail_rate` / `source` 字段）
- 申万板块清单有 `sw2021_sectors.py` 作为权威来源，不是凭记忆编造

### 2.2 历史数据估算问题 ★★☆☆☆ —— 核心风险点

**这是当前项目最大的数据准确度隐患。**

**当前做法（`collect_daily_records`）：**
```python
# T-1 到 T-(n-1) 的历史净流入 = (MainNetFlow5D - 今日净流入) / (n-1)
net_4d = net_5d - today_net
avg_daily = net_4d / (n - 1)
# 每条历史记录都填同样的平均值！
```

**问题分析：**

| 问题 | 详情 |
|------|------|
| **平均化失真** | 假设近 5 日累计 = 10 亿，今日 = 2 亿，则 T-1~T-4 全部填 2 亿。实际上某天可能是 +5 亿，某天 -1 亿，平均化抹平了波动，导致近 3 日和近 5 日的净额率计算结果与实际差异大 |
| **n 越大误差越大** | n=20 时，近 19 天历史全填同一个均值，图表变成一条水平线，毫无信息量 |
| **累计字段不够用** | westock 只给 5D/10D/20D 三档累计，没有"逐日拆开"的接口。当前方案是"有总比没有好"的妥协，但用户看到的近 n 日柱状图（除了今日那根）本质上全是假数据 |
| **交易日历缺失叠加** | 计算 `date` 用的是 `timedelta(days=i)`，周末被当成交易日填入。6 月 28 日（周一）的 T-1 会被填成 6 月 27 日（周日），虽然 `estimated: true` 标注了，但日期本身就是错的 |

**建议方案（按优先级）：**

1. **立即修复**：引入交易日历，确保历史记录的 `date` 字段跳过非交易日
2. **短期**：利用 5D/10D/20D 三档累计值做 2 段差分——
   - T-1~T-4 日均 = (5D - 今日) / 4
   - T-5~T-9 日均 = (10D - 5D) / 5
   - T-10~T-19 日均 = (20D - 10D) / 10  
   这至少能让图表呈现阶梯状变化，而不是全平
3. **中长期**：每日收盘后自动跑一次 `collect_minute_snapshot` 的最后一个分钟点作为日级快照，存入新表 `daily_close`，逐步积累真实历史

### 2.3 成交额计算 ★★★☆☆

**当前方案：** `calc_turnover` 默认 method="main"，即 `成交额 = MainInFlow + MainOutFlow`（主力口径）。

**问题：**

| # | 问题 | 详情 |
|---|------|------|
| T1 | **主力口径 ≠ 全市场成交额** | 主力成交额只占全市场的一部分（通常 10-30%），用它做分母算净额率会系统性偏高。例如某板块主力净流入 1 亿、主力成交额 10 亿 → 净额率 10%；但全市场成交额可能是 50 亿 → 真实净额率只有 2%。这个偏差在小盘板块尤为显著 |
| T2 | **method 不可配** | `calc_sector_metrics` 和 `calc_sector_metrics_batch` 都硬编码 `method="main"`，用户无法切换为 "all"（主力+散户全口径）。虽然全口径也不等于全市场成交额（缺少中单/大单之间的部分），但至少比主力口径更接近真实 |
| T3 | **历史成交额完全缺失** | T-1 及更早的 `turnover=None`，`_build_summary` 中用了 `today_turnover` 或 `circ_mv * 2%` 兜底。但 2% 日均换手率是一个拍脑袋的经验值，不同板块差异极大（银行 0.3% vs 半导体 5%+），导致历史净额率失真 |

**建议：**

- 在 `config.py` 加 `TURNOVER_METHOD = "all"` 配置项，默认改为全口径
- 历史成交额兜底不应一刀切 2%，至少按规模分档：大盘 1%、中盘 2%、小盘 3%
- 考虑在 README 中加"数据精度说明"章节，告知用户净额率是基于主力口径估算，并非交易所官方数据

### 2.4 流通市值精度 ★★★☆☆

**方案 A（Tushare）：** `daily_basic` 接口拿个股 `circ_mv` 字段直接累加。**这是相对最准的数据源**，但有以下局限：
- 需要有效 Tushare Token（需用户自行注册，有积分门槛）
- `daily_basic` 数据有 T+1 延迟，盘中无法实时更新
- `_find_valid_trade_date` 只往前回溯 7 天，长假（如国庆 7 天 + 周末 = 9 天无数据）会拿到 0 条记录，直接回退方案 B

**方案 B（westock 反推）：** `MainInflowCircRate = |MainNetFlow| / circ_mv * 100` 反推。
- 精度取决于 `MainInflowCircRate` 字段的小数位数（实测最小 0.01%），个股净流入 10 万时反推出的流通市值误差可能达数亿
- 已做了噪声过滤（`MIN_CIRC_RATE=0.001`, `MAX_CIRC_RATE=50`, `MAX_SINGLE_STOCK_MV=5e12`），控制住了离群值
- 但小盘股 + 低换手日，反推结果仍有 ±20% 的波动

**问题总结：**

| 问题 | 影响 | 建议 |
|------|------|------|
| 无 Tushare 时依赖反推，精度不够 | 大/中/小盘分档可能错位（边缘板块如 0.98 万亿被分到小盘），导致使用错误的阈值做强度判定 | 在 `sector_circ_mv` 表中记录 `is_estimated`，前端对源自"反推"的流通市值加 Tooltip 提示 |
| 长假后回溯窗口不足 | 方案 A 拿不到数据，全板块回退方案 B，但用户无感知 | `_find_valid_trade_date` 的 lookback 至少延长到 15 天 |
| 成分股采集失败无重试 | `collect_constituents_all_sectors` 失败则板块无成分股列表，流通市值也为空 | 加指数退避重试 |

### 2.5 分钟级差分 ★★★☆☆

**做法：** 每分钟调一次 fund flow，拿 `MainNetFlow` 当日累计值，与上一分钟快照差分得到 `minute_delta`。

**问题：**

| # | 问题 | 详情 |
|---|------|------|
| D1 | **不是真"分钟级"** | README 自己也说明了："通过差分得到，本质不是真分钟级"。由于接口只返回累计值，差分值是两次调用的增量，但如果接口数据有微小的浮点抖动或延迟，差分值会包含噪声。更关键的是，**两次调用之间的成交量可能不完全是这 60 秒内的**（接口本身有缓存/延迟） |
| D2 | **开盘第一分钟无差分** | 9:30 第一条快照的 `minute_delta = main_net_flow - 0`，等于当日累计。后面才是真正的分钟增量。前端图表上第一根柱子会异常高 |
| D3 | **成交额差分缺失** | 只对 `main_net_flow` 做了差分，`turnover` 是每分钟的当日累计值，没有差分出本分钟成交额。前端分钟图只能显示累计成交额折线，无法展示每分钟成交额柱状图 |

**建议：**
- 对 `turnover` 同样做差分，让分钟图可以同时展示"本分钟净流入"和"本分钟成交额"
- 过滤开盘第一条的异常差分值（或标记为 `is_open_anchor: true`）

### 2.6 边界情况 ★★★☆☆

| 场景 | 当前行为 | 问题 |
|------|---------|------|
| **westock CLI 全挂** | `fund_flow` 返回空列表 → `flow_map = {}`，所有板块今日数据全为 None | 前端显示全为 "-"，用户不知道是接口挂了还是真的没数据。建议在 `errors` 中区分"无数据"和"接口异常" |
| **部分板块无数据** | 134 个中只有 80 个返回 → 其余 54 个被静默跳过 | `errors` 里只有 `westock_low_coverage` 标记，前端不展示。建议在 `/api/sectors` 响应中加 `coverage_rate` 字段 |
| **n=20 时数据极稀疏** | n=20 但接口只到 20D 累计，历史 19 天全部平均估算 | 用户选 n=20 时看到 19 条完全相同的柱状图，体验差。建议 n>5 时在图表上加警告标注 |
| **流通市值为空时强度判定** | `_calc_strength_from_records` 中 `circ_mv_yi is None` → 直接返回 `level="普通"` | 合理的兜底，但前端不区分"真普通"和"无数据所以普通"，建议加 `strength_confident: false` |

## 三、展示高可读性

### 3.1 整体布局 ★★★★☆

**优点：**
- 顶部统计卡片 + 宽表 + 底部对比图的布局符合"概览→详情→对比"的阅读顺序
- antd 组件统一了视觉风格，间距/字号一致性较好
- 深色强度标签（红=强、绿/蓝=弱）在白色背景下对比度足够

**问题与建议：**

| # | 问题 | 建议 |
|---|------|------|
| V1 | **宽度 1400px 的表格在小屏幕上需要横向滚动**，且"今日净流入"和"近5日净额率"之间隔了 5 列，需要来回拖拽 | 把最核心的 5 列（名称/今日净流入/今日净额率/近5日净额率/强度判定）设为固定列两端，中间列可滚动 |
| V2 | **流通值(亿) 和 今日净流入(亿) 数值差异大**（流通值 50000 亿 vs 净流入 0.05 亿），视觉上容易混淆量级 | 流通值加"万"或"亿"后缀，或对超大数值用 `(5.2万亿)` 格式 |
| V3 | **表格默认每页 50 行**，134 个板块分 3 页。但强度排序后，用户最关心的"强"板块在第 1 页，"弱"板块在第 3 页，可能看不到 | 默认排序改为"强度降序"（已是），但可以考虑加一个"只看强/偏强"的快速筛选按钮 |

### 3.2 色彩与视觉编码 ★★★★☆

**强度标签配色：**
```
强    #e74c3c (红)   —— 暖色，符合"强=好"的直觉
偏强  #f39c12 (橙)   —— 过渡色
普通  #95a5a6 (灰)   —— 中性
偏弱  #3498db (蓝)   —— 冷色
弱    #2c3e50 (深蓝) —— 冷色
```

**问题：**
- "弱"用深蓝 `#2c3e50`，在小字号下几乎呈黑色，与"偏弱"的亮蓝 `#3498db` 区分度不够。建议"弱"用深绿 `#27ae60` 或保持蓝色但加粗/加边框
- "强"的红 `#e74c3c` 与 A 股红色=涨 一致，但"弱"的深蓝在一些行情软件中代表"平盘/中性"，语义有歧义

**净流入着色：**
```
正 → 红色 #e74c3c (中国习惯：红涨)
负 → 绿色 #2ecc71 (中国习惯：绿跌)
```
正确，符合国内用户习惯。但注意部分国际产品红跌绿涨，这里与 A 股惯例一致。

### 3.3 图表可读性 ★★★☆☆

**`DailyHistoryChart`（近 n 日柱状图）：**
- **问题 1**：历史日均估算值完全相同时，柱状图变成 4 根完全一样的柱子 + 1 根不同的柱子，视觉上非常奇怪。建议在柱子上标注 `estimated` 或加虚线边框区分
- **问题 2**：y 轴自动缩放，如果某天净流入是 +50 亿，另一天是 -30 亿，柱子会撑得很高，看不清小额变化。建议加参考线（y=0）

**`MinuteChart`（分钟级折线图）：**
- **问题 1**：3 条线（累计净流入、本分钟增量、累计成交额）放一起过于拥挤。建议把成交额放到另一个 Y 轴（已做），但最好拆成上下两个子图
- **问题 2**：本分钟增量是柱子，柱子的正/负颜色应该与净流入一致（红正绿负），当前全蓝 `#3498db`

**`NetRateCompareChart`（Top15 对比图）：**
- 横向柱状图方向正确（便于阅读板块名称）
- 但是近 3 日和近 5 日两组柱子贴在一起，当数值接近时几乎重叠。建议改成分组柱状图或上下两个独立条形图

### 3.4 信息层级 ★★★☆☆

**当前信息密度（每行 13 列）：**
```
名称 | 代码 | 流通值 | 规模 | 今日净流入 | 今日净额率 | 近3日净流入 | 近3日净额率 | 近5日净流入 | 近5日净额率 | 强度判定
```

**问题：**
- 近 3 日净流入和近 5 日净流入高度相关，通常数值接近，可以只保留净额率+一个净流入（如"近5日净流入"），减少 2 列
- "代码"列（如 `pt01801081`）对最终用户几乎无意义，建议隐藏或 hover 才显示
- 建议精简为 8 列核心列：
  ```
  名称 | 流通值 | 今日净流入 | 今日净额率 | 近5日净额率 | 走势迷你图 | 强度
  ```
  其中"走势迷你图"可以用 sparkline 替代展开操作，一眼看到近 5 日趋势

### 3.5 前端性能 ★★★☆☆

- **无虚拟滚动**：134 行还好，但如果扩展到全 A 股 5000+ 只个股会卡。antd Table 在 134 行没问题
- **每次展开都重新请求**：合理，但 `rowExpandable: () => true` 意味着所有 134 行都可以展开，用户可能误点。建议只有点击名称才展开
- **ECharts 实例未销毁**：`expandedRowRender` 中每次展开都创建新的图表实例，关闭时不销毁。虽然 `echarts-for-react` 有内置清理，但在快速切换展开行时可能残留。建议在 `onExpand` 中主动 `dispose`

## 一、缺陷清单（按危害聚类，非按修复难度）

### A 类：强度判定口径分裂 —— "展示的是一套，算的是另一套"

**A1 · 强度判定 n 与用户切换的 n 解耦**
- **定位**：`data_cache.py:338` `check_strength_alerts` 用 `calc_sector_strength(records, circ_mv_yi, STRENGTH_WINDOW_N)`——固定写死 n=5；而用户在 Header 切到 n=10/20 时，宽表展示强度是按 actual_n 算的（`app.py:488`）。
- **危害**：告警的"原档位/新档位"用 n=5 算，用户看宽表强度用 n=10 算——同一板块可能宽表显示"偏强"但告警写"普通→偏强"，用户认知崩裂。
- **为何是产品设计问题**：告警是给用户用的产品功能，不是开发者诊断。它的判定口径必须与用户当前观测口径一致，否则告警本身就成了噪声源。这是"接口能力驱动"的典型——后端把告警检测做完了（最难的部分），却没接上用户的主观测口径。

**A2 · 概念板块强度判定输入与展示输入不一致**
- **定位**：`app.py:668` `strength_records = cached_daily[:n] if cached_daily else [today_rec]`——强度判定取前 n 日真记录；但展示的 `summary_5d` 只取 `records_5d[:SUMMARY_5D]`（前 5 日）。当 n=10/20 时，强度判定输入远多于展示输入。
- **危害**：用户在概念 Tab 看"近5日净额率 3%"，但强度档位标签显示"强"——因为强度是按近10日算的。用户无法把强度档位与眼前任何一列数字对应起来。
- **为何是产品设计问题**：强度的可解释性要求"判定依据 = 展示依据"。展示 5 日汇总却用 10 日判强度，等于让用户看着一张表里的两个互不相干的口径。这不是算法 bug（算法本身正确），是产品叙事的断裂。

**A3 · `calc_aggregate_net_rate` 成交额兜底用今日值覆盖历史日**
- **定位**：`strength.py:175-178`——历史日成交额缺失时，先用 `today_turnover` 补齐，再用 `circ_mv × 换手率` 补齐。
- **危害**：盘前（9:15 前）今日成交额=0，所有历史日成交额被兜底成 0 → 净额率分母为 0 → 算法返回 None → 强度默认"普通"。盘前看板全员"普通"，强度排行失效。即便盘后，今日成交额 ≠ 历史日成交额（板块日成交额波动可达 2-3 倍），用今日值兜底历史日会让净额率系统性偏高或偏低。
- **为何是产品设计问题**：产品承诺"近 n 日聚合净额率判定强度"，但实现里这个聚合率在盘前完全失效、盘后系统性失真。用户看不到"盘前强度不准"的任何提示——Header 的数据源体检徽标只 ping 接口活性，不检测算法有效性。这是"接口能力驱动"——成交额字段缺失就兜底，兜底值不合法也照算，没人问"这个兜底值对产品承诺的净额率有没有意义"。

### B 类：告警功能 —— "后端就绪 ≠ 产品闭环"

**B1 · 告警检测阈值无法配，只能配展示过滤**
- **定位**：`data_cache.py:302` `check_strength_alerts`——全板块无条件检测档位变化写入；`app.py:1417-1440` `/api/alerts` 的用户阈值（`strength_up`/`levels`/`codes`）只是**展示侧过滤**，不参与检测。
- **危害**：用户设"仅看强度 ≥ 1.0"——这只过滤展示，告警库里仍堆积全部板块的档位抖动（普通↔偏强来回切）。告警库膨胀，前端 AlertsTab 拉一次 200 条全是噪声。用户真正想要的"只在升到偏强以上时提醒我"无法实现。
- **为何是产品设计问题**：告警的"阈值"在产品语义上有两种——**触发阈值**（什么时候写告警）和**展示阈值**（看哪些已写的告警）。工程把两者混淆，只做了后者。用户配的阈值在产品叙事里是"触发阈值"（"我要的是提醒，不是事后翻账本"），实现却是"展示阈值"。这是接口能力驱动——后端检测做完了，前端过滤加上了，但两者的产品语义没打通。

**B2 · 告警无盘中即时推送，只有事后翻账本**
- **定位**：`AlertsTab.jsx`——纯拉取式表格，`loadAlerts` 仅在 Tab 切入或手动刷新时调；无轮询、无 SSE、无 WebSocket。
- **危害**：盘中某板块"普通→强"时，用户必须自己点进告警 Tab + 手动刷新才能看到。告警的核心价值是"及时知道"，这个实现是"事后查阅"。
- **为何是产品设计问题**：告警 Tab 的产品定位应该是"盘中被动接收信号"，实现成了"主动查阅历史"。同样是被动接收——Header 的数据源体检徽标做了轮询（30s health），告警却没做。工程对"开发者诊断面板"（数据源）的即时性投入比对"用户产品功能"（告警）还多。

### C 类：可解释性 —— "标签能 hover，但 hover 出来的是空话"

**C1 · `StrengthTag` 的可解释性参数在所有调用点都没传**
- **定位**：`ui.jsx:20` `StrengthTag` 签名有 `scale/windowN/netRate` 三个可解释性参数；但所有调用点——`L1Tab.jsx:121`、`App.jsx:512`、`AlertsTab.jsx:118/121`、`SectorDetail.jsx`——都是 `<StrengthTag level={...} value={...} />`，三个参数全缺。
- **危害**：hover 出来的 tooltip 永远是"强度值 X · 规模档：小盘（阈值...）· 窗口：近 undefined 日聚合净额率"——"undefined"直接漏给用户看。即便不漏，"小盘"也是硬编码默认值（concept 板块 `circ_mv=None` → 永远小盘），不是真实规模档。
- **为何是产品设计问题**：可解释性的产品价值是"用户能从标签追溯到判定依据"。这里加了可解释性的壳（函数签名）但没接通数据流——每个调用点都拿得到 `scale` 和 `n`（在 record 里或闭包里），但没人传。这是"接口能力驱动"的极端形态：组件能力做完了，集成侧零接入。

**C2 · n 日窗口的 Header 单选缺上下文，用户不知道切了影响什么**
- **定位**：`App.jsx:538-548` Header 的 `<Select value={n}>`——单一下拉，无 tooltip、无说明、无"切了影响哪些 Tab"的提示。
- **危害**：用户切 n=10——二级板块宽表强度重算、一级行业聚合重算、概念板块强度重算、告警判定**不变**（A1）、对比 Tab 不变。用户不知道 n=10 到底影响了什么，也不知道告警为什么没跟着变。
- **为何是产品设计问题**：n 是这个产品的核心观测口径旋钮，它影响 4 个地方但有 2 个例外（告警/对比）。产品应该在旋钮旁明确告知"本旋钮影响宽表强度/聚合，不影响告警与对比图"——否则用户会建立错误的心智模型（"我切了 n 告警也该变"）。

### D 类：数据时效叙事 —— "盘前全员普通，没人告诉用户为什么"

**D1 · 盘前强度全员"普通"，无降级标注**
- **定位**：A3 的后果——盘前 `today_turnover=0` → 历史日成交额兜底为 0 → 净额率 None → `calc_sector_strength` 默认 `"普通"`（`strength.py:240`）。
- **危害**：盘前（9:15-9:30）用户打开看板，134 个二级板块 + 全部概念板块强度档位全是灰色"普通"，强度排行也全是"普通"。用户以为系统坏了或数据没采到——实际是算法兜底失效。
- **为何是产品设计问题**：产品没在盘前给"普通"档位加任何降级标注（estimated 徽标只标概念板块缓存空 fallback，不标强度兜底）。用户看到全员"普通"时，产品应该明确说"盘前成交额未就绪，强度暂不可判"——而不是让用户自己猜。这是数据时效的产品叙事缺失。

**D2 · 分钟数据缓存保留期文档与默认值再次分裂**
- **定位**：`config.py:110` `MINUTE_CACHE_DAYS=2`（注释写"用户要求 2 个交易日即可"）；`README.md:33` 写"仅缓存最近五日"；`config.py` 顶部 `MINUTE_CACHE_DAYS` 配置表（README:186）写"默认 5"。
- **危害**：README 说 5 日、config 默认 2 日——用户按 README 预期盘后能看近 5 日分时，实际只有 2 日。盘后第 3 天想复盘前天分时图，数据已被 `cleanup_old_minute_data` 清掉。
- **为何是产品设计问题**：这是第二轮评审就标过、宣称已修、现在又回退的缺陷。`647deed` 改成 2，`391c189` 改回 5，后续某次提交又改回 2（config 现值 2 + 注释明确"2026-08-11 用户要求 2 日"）。产品决策在反复，但 README 没跟着同步——用户视角的承诺（5 日）和实现（2 日）分裂。

### E 类：启动与首屏 —— "默认 Tab 是概念板块，不是主看板"

**E1 · 默认 Tab 是"概念板块"而非二级板块主看板**
- **定位**：`App.jsx:41` `useState("concept")`——首屏默认切到概念板块 Tab。
- **危害**：产品的核心叙事是"申万二级板块资金流监控"（README 标题），二级板块宽表是主看板。但首屏默认给概念板块——概念板块是辅助观测（量小、变动快、与二级板块代码空间隔离），不该占首屏。新用户打开看到概念板块宽表，会误以为这就是产品全部。
- **为何是产品设计问题**：首屏 Tab 选择是产品叙事的入口。工程选"concept"可能是因为概念板块路由不依赖 data_cache 预热（`app.py:577` 注释明说），即"接口能力驱动"——哪个 Tab 数据就绪快就默认哪个，而非"哪个 Tab 是产品主叙事就默认哪个"。

**E2 · Header 按钮密度过载，主次不分**
- **定位**：`App.jsx:583-660` Header 右侧一排 7 个交互元素：n 选择 + 数据源徽标 + 刷新 + 采集 + 刷新板块列表 + 刷新概念 + 错误日志图标。
- **危害**：用户首屏看到 7 个按钮，分不清"刷新"（刷宽表数据）和"刷新板块列表"（刷板块清单）和"刷新概念"（补全概念白名单）的区别——三个都叫"刷新"，语义完全不同。采集按钮对普通用户无意义（开发者诊断）却和主操作并排。
- **为何是产品设计问题**：Header 是全局操作区，应该主次分明——主操作（刷新宽表）突出，诊断/管理操作（采集/刷板块清单/刷概念/错误日志）收进二级菜单或设置抽屉。现在全平铺，是"接口能力都做了就都摆出来"的接口能力驱动思维。

### F 类：文档与实现分裂 —— "README 描述的是另一个工程"

**F1 · README 项目结构注释严重过期**
- **定位**：`README.md:60-68` 列了 `tencent_api.py`/`start.sh`/`realtime_strength.py` 三个文件——`tencent_api.py` 不存在（腾讯接口已死，collector 注释明说改用 westock 自身成交额字段），`start.sh` 已被 `dev.sh` 取代（README:94 却还写`./start.sh`），`realtime_strength.py` 实际在 `doc/` 下而非项目根。
- **危害**：新用户按 README 找 `start.sh` 启动 → 找不到 → 困惑。按 README 找 `tencent_api.py` 看成交额来源 → 不存在 → 以为项目残缺。
- **为何是产品设计问题**：README 是产品的门面。它描述的是一个已经不存在的工程版本——这本身就是产品叙事失真。工程演进了（dev.sh 取代 start.sh、腾讯接口下线、realtime_strength 归档），README 没跟着更新——典型的"接口能力变了但产品叙事没同步"。

**F2 · README 数据源描述与实现矛盾**
- **定位**：`README.md:3` 写"腾讯原始 HTTP 接口"；`README.md:24` 架构图写"腾讯原始 HTTP (requests) → turnover 成交额 + circ_mv"；但 `collector.py:232` 注释明说"腾讯原 HTTP 接口已死，净额率改用 westock 自身字段计算"，`circ_mv_collector.py` 走的是 Tushare 不是腾讯。
- **危害**：用户按 README 理解数据源是腾讯 HTTP，实际是 westock CLI + Tushare。数据源体检徽标（Header ApiOutlined）显示的是真实三源（westock/tushare/trading_calendar），与 README 描述完全对不上。
- **为何是产品设计问题**：数据源是监控产品的根基，用户必须知道数据从哪来才能信任。README 描述的数据源链路与实际不符——这不是笔误，是产品叙事与实现长期分裂没人维护。

## 三、一句话总结

**这个工程的系统性病灶是"接口能力驱动"——后端把检测/缓存/可解释性/体检的最难部分都做完了，但产品叙事侧（强度判定与展示口径对齐、告警的触发语义、可解释性参数的实际接入、盘前降级标注、README 与实现同步）系统性轻视，导致用户看到的是一个"功能都在但口径对不上、标签能 hover 但 hover 出空话、告警能写但写的不是用户配的阈值"的工程。**

P0 四条（A3/B1/A1/D1）是核心指标和核心产品语义的失效，应优先修复。

## 一、产品设计层面

### 1.1 概念板块是"产品承诺了，但实现是空壳"

**现状**：概念板块宽表（626 个）是主界面默认 Tab，产品形态与二级板块完全一致（净流入/净额率/近3日/近5日/强度/行展开分时图）。

**问题**：
| # | 现象 | 根因 |
|---|------|------|
| C-1 | 概念板块分时图永远只有一个点（实时快照），没有真实分钟折线 | 采集器 `collector_loop` 只采集二级板块（`get_sector_codes()` 返回 pt018），概念板块（pt02）不在分钟采集范围。`/api/sectors/{code}/minute` 对 pt02 走 `fund_flow` 单点兜底 |
| C-2 | 概念板块近5日净流入用 `MainNetFlow5D` 累计值均分估算，近3日用 `concept_daily` 缓存真实累加——**同一张表两套口径** | 用户曾要求"近3日走缓存、近5日保持 API 原值"，产品层缺乏统一的数据口径定义 |
| C-3 | 626 个概念板块是 8 月 10 日一次性扫描的静态快照，腾讯概念板块**动态增减**（2026 年新增词元/稳定币/敦煌网等），无自动发现机制，快照会过时 | `concept_sectors.py` 是硬编码 dict + 一次性扫描结果，无周期性扫描任务 |
| C-4 | 10 个申万板块（社交Ⅱ/本地生活服务Ⅱ/其他银行Ⅱ等）腾讯无数据，前端照常显示为"无数据"，产品上没有任何"该板块无数据源"的标识 | 无覆盖标记字段 |

**改进措施**：
1. **概念板块纳入分钟采集**：`collector_loop` 每 N 轮补采一次概念板块分钟快照（626 码 fund_flow 约 10-15s，可每 5 分钟一轮），分时图才有真实折线。
2. **统一近N日口径**：产品层明确"近N日净流入"唯一算法（建议统一走 `concept_daily` 真实日记录累加，API 累计值只作为校验），前端表格列名标注"真实累计/估算"。
3. **概念板块自动发现**：新增周期性扫描任务（如每周一次），扫描 pt02 新区间并增量合并，避免静态快照过期。
4. **无数据源标识**：`sector` 返回加 `data_source: "westock"|"none"` 字段，前端无数据源板块灰显 + Tooltip 说明。

### 1.2 数据缺失与接口异常不区分

**现状**：`fund_flow` 在 CLI 挂掉时返回空列表，与"板块确实无数据"（10 个不覆盖板块）在 API 层都是 `sectors=[]` 或 `net_flow=None`。

**问题**：前端无法区分"接口挂了"和"真没数据"，用户看到一片"-"不知道是系统故障还是正常情况。

**改进措施**：`collector`/`app` 增加 `data_health` 指标（coverage_rate、last_error、source_status），`/api/health` 已部分具备（cache_init/refresh_last_error），前端顶部加"数据源健康"状态灯。

### 1.3 历史回看缺失，攒了数据用不上

**现状**：`concept_daily` 已按日存储概念板块净流入（保留 20 交易日），`minute_snapshot` 存分钟数据（保留 2 日），但 API 层**没有任何历史日期查询**——`/api/sectors/concept` 只能看今日，`/api/sectors/{code}/minute` 只能查今日。

**问题**：用户无法回看"上周五某概念板块的强度/净流入"，无法做复盘和策略验证。数据已经入库却无出口。

**改进措施**：`GET /api/sectors/concept?date=YYYYMMDD` 支持历史日期（读 concept_daily 缓存），`GET /api/sectors/{code}/minute?trade_date=` 已支持历史但前端 UI 没有日期选择器。

### 1.4 告警无推送渠道

**现状**：`alert_log` 表记录强度档位突变，前端有 AlertsTab 展示，但**没有任何推送**（站内通知/邮件/Webhook 都没有）。

**问题**：告警是投资决策信号，用户不会主动打开页面盯着看，纯日志展示等于无告警。

**改进措施**：P2 阶段支持企业微信/钉钉/Server酱 Webhook 推送，或在页面顶部做未读告警红点。

### 1.5 登录态与 401 噪音

**现状**：未登录时前端自动调 `/api/user/prefs` 等用户接口，后端返回 401，浏览器 console 每 30s 刷一条错误。

**问题**：日志噪音大，且用户不知道这些功能需要登录（Supabase）才能用。

**改进措施**：前端在未登录时不发起用户接口请求（AuthGuard 已存在但 prefs 加载在 guard 之外），后端对无 token 的 `/api/user/*` 返回 200 + `{logged_in: false}` 而非 401。

### 1.6 产品定位发散

**现状**：从"申万二级板块资金流监控"逐步演化为"二级板块 + 概念板块(626) + 分时对比 + 告警 + 自选 + 用户偏好 + Supabase 登录"，功能持续叠加。

**问题**：核心卖点（板块资金流监控）与周边功能（登录/自选/偏好）边界模糊，每个功能的维护成本都在摊薄核心链路质量。本会话 30+ 次故障中，约 1/3 来自边缘功能（错误日志页、用户偏好、概念板块兜底链）。

**改进措施**：明确产品核心路径（宽表 → 下钻 → 分时），周边功能标记为"实验性"并在 UI 上弱化，避免边缘功能拖垮核心稳定性。

## 二、架构层面

### 2.1 数据源无抽象层

**现状**：`westock` CLI 的调用散落多处——`app.py`（概念板块实时、单板块详情、分钟对比）、`collector.py`（分钟采集、日采集、概念日快照）、`data_cache.py`（预热）。曾尝试引入东方财富 fallback 又因口径不一致移除，`eastmoney.py` 已删除。

**问题**：
- 每次新功能都要在 `app.py` 里 `from westock import fund_flow`，重复拼装 flow_map、字段映射逻辑（`code`/`SecuCode`/`_sf` 转换散落 3 处）
- 没有 DataProvider 抽象，未来想换/加数据源（东方财富、Tushare）要改所有调用点
- 10 个腾讯无覆盖板块的"无数据"判断逻辑没有统一入口

**改进措施**：新增 `data_source.py` 抽象层：
```
DataSource.get_sectors() -> List[SectorRecord]   # 统一返回 code/name/l1/net_flow/turnover
DataSource.get_daily(codes, n) -> Dict[code, List[DailyRecord]]
```
`westock.py` 实现该接口，`app.py`/`collector.py` 只依赖抽象层。

### 2.2 缓存体系割裂，四种缓存各自为政

**现状**：
| 缓存 | 载体 | 用途 | 生命周期 |
|------|------|------|---------|
| `data_cache` | 内存 dict | 二级板块宽表 | 启动预热 + 60s 刷新 + 30s 重试 |
| `_concept_cache` | 内存 dict | 概念板块宽表（15s TTL） | 15s 过期 |
| `concept_daily` | SQLite | 概念板块日记录（近20交易日） | 收盘快照 + 20 天清理 |
| `minute_snapshot` | SQLite | 分钟K线（2日） | 60s 采集 + 2 天清理 |

**问题**：四种缓存无统一失效/一致性管理。概念板块宽表 15s 内存缓存与 concept_daily 日缓存并存，同一板块数据可能来自两个不同时间的快照；二级板块宽表与概念板块宽表的"近3日"算法还不一致。

**改进措施**：引入统一 CacheManager（TTL + 过期回调 + 统计），各业务缓存注册进去；宽表数据统一从"日记录缓存 + 实时"合成，消除同表多口径。

### 2.3 单 worker 阻塞是系统性隐患

**现状**：uvicorn 单 worker（`dev.sh`/service 均无 `--workers`）。概念板块 626 码 `fund_flow` 耗时 10-15s，期间**所有**其他请求（health、二级板块宽表）被阻塞。本会话已实测：`test.py` 在概念板块请求进行时 health 超时 60s。

**问题**：加 `--workers 4` 会导致采集线程重复启动（每个 worker 一个 collector_loop）、内存缓存互相独立——当前架构没有多 worker 的共享状态方案。这是"采集"与"API"强耦合的结果。

**改进措施**（二选一）：
1. **采集与 API 进程分离**：采集器独立进程（`python -m collector_loop` 或 systemd 独立 service），API 只读缓存/DB，彻底解耦——推荐，符合"采集永不阻塞展示"的产品要求。
2. 若保持单进程：概念板块宽表改为**后台任务 + 轮询**（`BackgroundTasks` 触发采集，前端轮询 `cache_updated`），API 层永远秒回缓存。

### 2.4 collector.py 职责过重（927 行）

**现状**：`collector.py` 同时承担：板块列表刷新、分钟采集（差分）、日级采集（分段估算）、概念板块日快照、流通市值采集、聚焦采集、交易时段判断、采集主循环。

**问题**：任何采集逻辑改动都在一个文件内牵一发动全身；`collect_concept_daily_snapshot` 是后加的，与分钟采集复用同一 `fund_flow` 但状态互不感知（各自维护去重标记）。

**改进措施**：拆分为 `collector_base.py`（fund_flow 封装/去重/重试）、`collector_minute.py`、`collector_daily.py`、`collector_concept.py`，主循环只做调度。

### 2.5 前端无数据层，组件自管状态

**现状**：`api.js` 只是 axios 封装，无 react-query/SWR。每个 Tab/组件各自维护 `loading/error/data` 状态（App.jsx 有 30+ useState/useCallback），错误处理、重试逻辑重复实现（loadSectors 与 loadConceptSectors 各写一套指数退避）。

**问题**：App.jsx 858 行持续膨胀；新增页面必须复制粘贴 loading/error 样板代码；已出现"成功路径漏关 loading"这类重复 bug（本会话修复过）。

**改进措施**：引入 `@tanstack/react-query` 或轻量 SWR，统一 `useQuery`/`useMutation`，删除手工重试样板。

### 2.6 部署体系单一脚本职责过载

**现状**：`dev.sh` 同时承担：杀旧进程、检测 systemd、装依赖、编译前端、安装 git hook、启动服务、验证健康——一个脚本 285 行干 7 件事。`westock-monitor.service` 硬编码 `/root/westock-monitor` 路径。

**问题**：本会话已暴露多次部署问题（kill 顺序、systemd Restart 复活、端口占用），单一脚本把所有故障点挤在一起；路径硬编码导致换机器/换目录必坏。

**改进措施**：拆分为 `install.sh`（首次部署）/ `start.sh`（启动）/ `stop.sh`（停止）/ `test.py`（验证）；service 文件路径由 `install.sh` 动态写入而非硬编码。

### 2.7 无 CI，测试靠人肉

**现状**：`test.py` 只能本地手动跑；`tests/` 目录仅 2 个文件（test_collector.py/test_strength.py），无 pytest 接入、无 GitHub Actions。

**问题**：本会话所有回归（storage NameError、TURNOVER_METHOD 缺失、loading 不关）都是用户在生产环境发现后才修的——没有任何自动化防线。

**改进措施**：GitHub Actions：`python -m pytest tests/` + `python test.py`（起服务后）+ `cd frontend && npm run build`，main 分支 PR 强制通过。

## 三、代码落地层面

### 3.1 test.py 是冒烟测试，不是单元测试

**现状**：`test.py` 覆盖 13 项：API 端点 200、进程日志无崩溃、4 张表存在、关键字段非空。**不覆盖任何计算逻辑**。

**问题**：`calc_turnover`（成交额口径）、`_build_summary`（近N日汇总）、`strength.py`（5档判定）、`collect_daily_records`（分段差分）这些最容易出错的纯函数**零测试**。本会话修复的"成交额双边重复计算"（翻倍 bug）就是这类逻辑错误，测试套件完全拦不住。

**改进措施**：
- 纯函数单测：`calc_turnover(main/all/auto)`、`_build_summary`（含成交额兜底链）、`_calc_strength_from_records`、`_to_yi`
- mock fund_flow 返回，测 `get_concept_sectors` 的 3 日缓存 vs 5 日估算逻辑
- 用 pytest fixture + 内存 SQLite，不依赖真实网络

### 3.2 单体文件过大

**现状**：`app.py` 1720 行、`collector.py` 927 行、`storage.py` 906 行、`App.jsx` 858 行。

**问题**：app.py 1720 行里 API 路由、缓存、日志、SPA 兜底、启动逻辑全在一起；storage.py 建表、读写、统计、清理全在一个类。维护时上下文切换成本极高。

**改进措施**：app.py 按域拆分（`api_sectors.py`/`api_minute.py`/`api_user.py`/`api_meta.py`）；storage.py 按表拆分。

### 3.3 错误处理不一致

**现状**：
- `get_concept_sectors` 曾因漏 `storage = get_storage()` 抛 NameError（本会话修复，触发 53 次进程重启）
- `get_errors` 里 `except Exception: pass` 静默吞日志读取失败
- `get_current_user` 里 `except Exception: return None` 掩盖一切异常
- 部分 `except Exception` 无 `exc_info=True`，日志只有一行错误看不到堆栈

**问题**：缺少统一的异常处理策略：哪些异常要记录、哪些要返回 5xx、哪些要静默降级，全靠写代码时的临场判断。

**改进措施**：FastAPI 全局 exception handler（记录 + 结构化日志 + 统一响应格式），业务代码只抛自定义异常，杜绝裸 `except: pass`。

### 3.4 fund_flow 重试逻辑嵌套过深

**现状**：`westock.fund_flow` 有 3 轮重试（并发批次 → 小批重试 → 逐个兜底），概念板块又在第 3 轮后追加东方财富兜底（已移除，但结构还在），`/api/minute/compare` 又有独立的快照兜底。

**问题**：调用链复杂，任何一层失败/超时都难定位；重试参数（批次大小、并发数、轮数）散落在 westock.py 和 config 里。

**改进措施**：重试逻辑抽成 `retry_fund_flow()` 装饰器/工具函数，统一日志（含 elapsed/codes/coverage），config 集中重试参数。

### 3.5 配置散落与硬编码

**现状**：
- `config.py` 有环境变量体系，但 `supabase_base.py` 里 `SUPABASE_ANON_URL = ""` / `SUPABASE_ANON_KEY = ""` 是空字符串硬编码
- 10 个无覆盖板块代码在 sw2021_sectors.py 的 `_FIX` 里，但"无数据源"标记无常量定义
- `.env.example` 存在但 `python-dotenv` 只在 requirements 里，代码没有 `load_dotenv()`

**问题**：`.env` 文件写了但从未被加载（`config.py` 只用 `os.getenv`，需要手工 export）；Supabase 凭据硬编码空串，未配置时静默降级成匿名访问，认证边界模糊。

**改进措施**：`config.py` 顶部 `from dotenv import load_dotenv; load_dotenv()`；Supabase 未配置时显式报错而非静默降级；无覆盖板块定义为 `UNCOVERED_SECTORS` 常量。

### 3.6 日志无结构化

**现状**：全部文本格式日志，无 trace_id、无 JSON 结构化、无 request_id 关联。

**问题**：跨请求排查（哪个前端请求导致 fund_flow 慢）要靠时间戳人工对齐；`/api/errors` 页面解析文本日志正则匹配，脆弱。

**改进措施**：结构化日志（JSON lines，含 request_id/session_id），/api/errors 直接读结构化日志。

### 3.7 魔法数字与隐含契约

**现状**：`FULL_EVERY_N = 7`（每 7 个聚焦周期补采）、`_CONCEPT_DAILY_KEEP = 20`、`max_retries = 10`、`WESTOCK_BATCH_SIZE = 20`、分段差分分母 4/5/10——多个魔法数字散落各文件，无注释说明推导过程。

**问题**：换手率兜底、分段分母等依赖 westock 字段口径的隐含契约（本会话已踩过：MainNetFlow5D 口径、成交额双边重复），一旦 westock 升级口径变化，无任何检测。

**改进措施**：所有魔法数字收拢到 config 或模块顶部常量 + 注释推导依据；对 westock 字段口径加运行时自检（`verify_fund_flow_fields()` 对比 5D 与逐日累加）。

### 5.2 新引入的阻断级回归（已修复）

**问题**：`concept_sectors.py` 新增 `search_and_merge_concepts(keyword: str) -> Dict[str, Any]` 使用了 `typing.Any`，但文件顶部 `from typing import Dict, List` **未导入 Any**。模块 import 时直接 `NameError: name 'Any' is not defined`，导致：
- `/api/sectors/concept` 全部 500（get_concept_sectors 内 `from concept_sectors import ...` 触发模块加载错误）
- collector 的 concept_daily_snapshot 也抛同样的 NameError

**实测**：本地服务跑 391c189 时 `GET /api/sectors/concept → 500`；修复 `from typing import Any, Dict, List` 后恢复 `total=626`。

**教训**：提交说明宣称"Python AST 全通过"，但 **AST 只查语法、不查名字解析**。任何新增函数使用了未导入的 typing 名称（Any/Optional/Set 等），AST 编译必然通过、运行时必然炸。需要 pyflakes/mypy 类静态检查才能拦住这类错误——这正是 v3 第 3.3 节"零单测、无静态检查"的系统性后果。
